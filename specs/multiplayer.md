# Lockstep multiplayer

## Turn order and authority

- **designed** — A match has 2–8 human seats. The lowest seat ID that has yet to end the round holds the controls. That player may issue regular orders, then hand over with `turn.end`. When the final seat ends, the simulation advances the round. A victory ends play immediately, including a victory between round boundaries.
- **designed** — The host binds the submitting player to the active seat and dispatches through the regular `MatchHost` player interface. The simulation checks the issuer, target visibility and game rules. Editor and setup commands are unavailable to multiplayer seats. Rejected orders leave the command sequence unchanged.
- **designed** — Shared-screen play uses a handoff screen on opening, resuming or changing seats in an unfinished match. The incoming player confirms before seeing their board or issuing an order. Play uses the seat's own observation. After victory the shared screen shows the public result.

## Command verification

- **designed** — A protocol-v1 position contains the number of accepted orders since hosting began (`u64`), the completed simulation round (`u32`) and the canonical simulation state hash (`u64`). A new host starts at sequence zero, including when hosting a saved game. The saved round and the seats that already ended it carry over.
- **designed** — A proposal names its exact prior position. The host accepts one command at that position and returns a versioned commit containing the submitting seat, the existing simulation command bytes, and the positions immediately before and after dispatch. Every acceptance increments the sequence by one, including an order that leaves the state hash unchanged. Repeating the original proposal after acceptance is stale.
- **designed** — Each replica verifies the version and prior position, decodes the command and independently dispatches it under the same player permissions. It installs the result only when the sequence, round and resulting hash match. A rejected commit leaves the replica at its last verified position. Its desync report identifies the seat, advertised prior position, expected and actual positions, and reason.
- **designed** — An opening carries the simulation save at the beginning of the current replay segment, the accepted commands since that save and the position after those commands. The replica restores the save, replays the suffix in seat order within the same round, and verifies the final position. This restores the host's current per-seat order counts even when a peer joins mid-round.

## LAN sessions and recovery

- **designed** — The native LAN host binds one distinct token of 1–256 bytes to each actual seat. Every join, synchronization and submission uses a fresh TCP connection and presents a protocol version, seat ID and token. The host processes authenticated match operations serially. Both the terminal and desktop clients present the authenticated seat's fog-filtered observation.
- **designed** — LAN wire version 2 binds write permits to one host instance and one seat. Joining the same seat replaces its previous permit. Recovery returns whether the host accepted the interrupted order and replaces the old permit while holding the match lock. After a host restart or expiry of the evidence needed to resolve an order, recovery reports that its outcome is unknown. The lockstep commit format remains at version 1.
- **designed** — The desktop client joins, synchronizes and submits orders on a background worker with one request in flight. While another seat is active it polls for updates. It enables orders when the local position is verified, the worker is idle and the authenticated seat is active. A stale submission or interrupted exchange requires synchronization before another order. The player can inspect the resulting position before deciding what to submit.
- **designed** — A native stdio MCP adapter joins the existing LAN host with one seat credential. It exposes player commands and resources, synchronizes observations and requests historical views through the host's seat-scoped replay API. World hashes, command sequence numbers and checkpoint cursors stay inside the trusted adapter. The player sees its own interrupted order's outcome. The adapter starts no opponents and never grants editor or spectator authority.

- **designed** — LAN peers are trusted with the entire world. A replica receives a full simulation save and other seats' committed orders to compute the canonical hash. A peer with access to its process can inspect hidden state. The TCP connection carries both credentials and match data in plaintext.
- **designed** — The host retains the last 128 commits. A peer supplies its last verified position to synchronize. For a retained boundary, the host verifies the round and hash, then sends the contiguous suffix through the current position. Matching sequence numbers with different rounds or hashes produce a desync refusal. After a submission reply is lost, the peer may issue another order once recovery verifies its position and the host guarantees that the original submission cannot arrive later and change that position.
- **designed** — A peer whose sequence predates the retained window receives an opening at the current position. The peer verifies it and reports the checkpoint transition, including the previous and restored sequences. A position ahead of the host receives a stale-position refusal.
- **designed** — A frame starts with a big-endian 32-bit payload length. The request JSON limit is 16 KiB and the reply JSON limit is 8 MiB. An opening's JSON header carries the current-round commands. A separate binary frame carries up to 40 MiB of save data. The server handles up to eight concurrent exchanges. Socket reads and writes share a ten-second deadline per exchange.
- **designed** — The shared match host permits 512 accepted non-ending orders per seat per round. A player may still end the turn when that allowance is exhausted. The match host keeps the most recent 32 completed replay rounds plus the current segment. A replica discards completed replay history after verification.

## Save and replay compatibility

- **designed** — Hosting an ordinary save uses the simulation's standalone-save rules and starts a new protocol history. The same rules apply to a position taken from historical playback. Archived replays retain the simulation semantics of their recorded format when played as replays. Multiplayer uses the existing state, command and replay formats.
